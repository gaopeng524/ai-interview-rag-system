# 11 · 测试（ChatResilienceServiceTest）

覆盖：怎么用 **Mockito mock 掉 ChatClient 的整条 fluent 链**，测流式重试逻辑。纯单元测试，**不发任何真实网络请求**。

## 一、为什么这 4 个测试值得写

`ChatResilienceService.streamChat` 是全项目最复杂、最容易出错的地方：流式 + 重试 + 降级 + 信封格式。手动打开浏览器测重试要等 30 秒+，还不可复现。单元测试把**每个行为分支**固定下来，改代码时一跑就知道有没有弄坏。

## 二、测什么 —— 4 个用例

| 测试 | 场景 | 断言 |
|---|---|---|
| `streamSuccess` | 正常流式，思考 + 正文两块 | 2 个信封：reasoning + content |
| `streamFailure` | 一开始就失败，重试耗尽 | 1 个 error 信封："AI 服务暂时不可用" |
| `streamRetryBeforeFirstChunk` | 首次失败→重试成功 | 只返回成功内容，`chatResponse()` 被调 **2 次** |
| `streamFailureAfterFirstChunkDoesNotRetry` | 吐了一半断了 | content + error，**不重试**（调 1 次） |

这四个用例正好覆盖了 `streamChat` 的三条逻辑路径：
- **全程成功** → 信封逐条出
- **一开始就挂** → 允许重试（因为还没吐过任何分片）
- **半路挂** → **绝不重试**（因为已经给浏览器看过内容，重试会重复回答），转 error

第 4 个用例尤其重要——它锁死了"**已输出就不重试**"这条安全语义。

## 三、核心难点：mock 一整条 fluent 链

`ChatClient` 是链式调用：`prompt() → user(msg) → toolCallbacks() → stream() → chatResponse()`。每步返回下一层的接口。测试要 mock **每一环**：

```java
ChatClient chatClient = mock(ChatClient.class);
ChatClient.ChatClientRequestSpec requestSpec = mock(ChatClient.ChatClientRequestSpec.class);
ChatClient.StreamResponseSpec streamSpec = mock(ChatClient.StreamResponseSpec.class);

// fluent 链逐步返回下一层
when(chatClient.prompt()).thenReturn(requestSpec);
when(requestSpec.user(anyString())).thenReturn(requestSpec);          // 返回自己
when(requestSpec.advisors(any(Consumer.class))).thenReturn(requestSpec);
when(requestSpec.toolCallbacks(any(ToolCallbackProvider.class))).thenReturn(requestSpec);
when(requestSpec.stream()).thenReturn(streamSpec);
```

**这里有个很隐蔽的坑**：`ChatClientRequestSpec` 有两个 `toolCallbacks` 重载——`toolCallbacks(List<ToolCallback>)` 和 `toolCallbacks(ToolCallbackProvider...)`。用 `any()` 不带类型时，Mockito 分不清匹配哪个，会抛歧义错误。**必须用带类型的 matcher** `any(ToolCallbackProvider.class)` 消歧。

## 四、构建被测对象 —— 生产构造器 vs 测试构造器

```java
ChatClient.Builder builder = mock(ChatClient.Builder.class);
when(builder.build()).thenReturn(chatClient);

// 真实注册天气工具（无外部依赖，直接 new）
ToolCallbackProvider weatherToolProvider = MethodToolCallbackProvider.builder()
        .toolObjects(new WeatherTools(RestClient.builder())).build();

// retryDelayMs=0，跳过重试等待，测试跑得快
service = new ChatResilienceService(builder, weatherToolProvider, 0L);
```

两个设计值得学习：
1. **工具是真实注册的**，不是 mock——`WeatherTools` 构造不需要网络/DB，`new WeatherTools(RestClient.builder())` 就能建，但它的 `getWeather` 只在模型"选择调用"时才触发，这些测试的 mock 流里没有工具调用，所以根本不会碰网络。
2. **`retryDelayMs = 0`** 是 [[05-Chat核心-流式与重试]] 里那个包私有构造器的意义：重试要退避等待（1s→2s），测试传 0 直接跳过，4 个用例跑完也就几毫秒。**测试专用构造器是"给生产逻辑留测试后门"的经典手法**。

## 五、喂真实数据 —— DeepSeekAssistantMessage

流式 mock 返回的不是随便的字符串，而是官方集成真实解析出来的消息类型：

```java
DeepSeekAssistantMessage reasoningMsg = new DeepSeekAssistantMessage.Builder()
        .reasoningContent("先思考").build();
DeepSeekAssistantMessage contentMsg = new DeepSeekAssistantMessage.Builder()
        .content("你好").build();

when(streamSpec.chatResponse()).thenReturn(Flux.just(
        new ChatResponse(List.of(new Generation(reasoningMsg))),
        new ChatResponse(List.of(new Generation(contentMsg)))));
```

`ChatResilienceService.toEnvelopes` 里有个 `instanceof DeepSeekAssistantMessage` 的分支（拿 `reasoningContent`）。**只有喂真实的 `DeepSeekAssistantMessage`，这个分支才会走到**——如果随便 mock 一个 `AssistantMessage`，思考信封的代码就测不到了。测试要尽量模拟真实对象。

## 六、断言方式

```java
List<String> result = service.streamChat("test-conversation", "你好")
        .collectList().block();    // Flux → List，同步取结果

assertEquals(2, result.size());
assertEquals("reasoning", typeOf(result.get(0)));
assertEquals("先思考", textOf(result.get(0)));
```

- `collectList().block()`：把响应式 `Flux<String>` 收集成 `List` 再阻塞取回——测试是同步的，能逐条断言。
- 断言信封：解析 JSON 取 `type` / `text` 字段，验证**信封格式和内容**都正确。
- `verify(streamSpec, times(2)).chatResponse()`：验证 `chatResponse()` **被调用了几次**——这是验证"重试了几次"最直接的证据。第 3 个测试断言 2 次（重试成功），第 4 个断言 1 次（不重试）。

## 七、这个测试类教你的三个习惯

1. **fluent 链要逐环 mock**：链式 API 测起来麻烦，但每个接口都 mock 成"返回自己/下一层"就不难。
2. **行为比状态重要**：`verify(times(2))` 比"结果对了"更能锁定"重试逻辑没被误删"。
3. **给生产代码留测试口子**（包私有构造器 + 参数化延迟）比硬编码一个值更利于测试。
