# 09 · 函数调用（Function Calling）与工具

覆盖：`WeatherTools` + `ToolConfig`。这是 AI 应用最经典的"**模型会自己决定查天气**"的机制。

## 一、什么是 Function Calling

模型本身**不能**联网、**不能**查实时数据。它的知识是训练时学的，不知道"今天北京多少度"。但模型很擅长一件事：**识别"这问题我得查一下才能答"**。

Function Calling 就是：**把"查天气"这个能力以函数的形态注册给模型，让模型在需要时主动调用它。**

```
用户："北京今天冷吗？"
        │
        ▼
   模型思考：这个问题需要实时天气 → 我该调用 getWeather(city="北京")
        │
        ▼
   Spring AI 执行 getWeather("北京") → 真的去 wttr.in 请求
        │
        ▼
   把结果"北京当前天气：晴，25°C…"回填给模型
        │
        ▼
   模型组织回答："今天北京晴，25 度，不冷，穿短袖就行。"
```

**关键点**：调用哪个函数、传什么参数，是**模型决定的**，不是代码写死的。代码只负责"注册工具 + 执行工具 + 回填结果"。

## 二、WeatherTools —— 注册一个工具

```java
@Component
public class WeatherTools {

    @Tool(description = "查询指定城市的当前天气情况")
    public String getWeather(@ToolParam(description = "城市名，例如：北京、上海，或拼音 Beijing") String city) {
        ...
    }
}
```

三个注解，含义明确：

| 注解 | 作用 |
|---|---|
| `@Component` | 让 Spring 把它当成 Bean 管起来（能被注入、被扫描） |
| `@Tool` | **声明这个方法是一个 AI 工具**。`description` 会被发给模型，模型靠它判断"这工具是干嘛的" |
| `@ToolParam` | 描述参数。模型靠它知道"该传什么" |

`description` 不是注释——**它会被发送给模型**。模型根据你写的描述决定什么时候调、怎么填参数。写得好不好，直接决定模型调用准不准。

## 三、ToolConfig —— 把工具打包成 Provider

```java
@Configuration
public class ToolConfig {
    @Bean
    public ToolCallbackProvider weatherToolProvider(WeatherTools weatherTools) {
        return MethodToolCallbackProvider.builder()
                .toolObjects(weatherTools)   // 扫描里面所有 @Tool 方法
                .build();
    }
}
```

Spring AI 需要一个 `ToolCallbackProvider`：它把 `WeatherTools` 里所有标了 `@Tool` 的方法，统一转换成一个一个"工具回调"，注册给模型。`MethodToolCallbackProvider` 是"**从方法自动生成工具定义**"的便捷方式——不用手写 JSON Schema。

这个 Bean 会在 [[05-Chat核心-流式与重试]] 里被注入：
```java
.toolCallbacks(weatherToolProvider)
```
挂上之后，模型在对话中就能主动调用 `getWeather` 了。

## 四、getWeather 内部 —— 真实请求 wttr.in

```java
String body = restClient.get()
        .uri(uriBuilder -> uriBuilder
                .path("/{city}")
                .queryParam("lang", "zh")    // 天气现象返回中文
                .queryParam("format", "j1")   // 完整天气 JSON
                .build(city))
        .retrieve()
        .body(String.class);

JsonNode current = objectMapper.readTree(body).path("current_condition").path(0);
String code = current.path("weatherCode").asText();
String desc = WEATHER_TEXT.getOrDefault(code,
        current.path("weatherDesc").path(0).path("value").asText());
```

- 用 **`RestClient`**（阻塞式客户端）发 GET：`https://wttr.in/北京?lang=zh&format=j1`。
- `format=j1` 返回完整 JSON，`current_condition` 里是实时天气。
- **`WEATHER_TEXT` 映射表**：把 wttr.in 的 `weatherCode`（如 `113`）翻译成中文"晴"。没匹配到的，退回 wttr.in 自己给的中文描述（`weatherDesc`）。

## 五、为什么要用 `Map.ofEntries` 而不是 `HashMap.put`

```java
private static final Map<String, String> WEATHER_TEXT = Map.ofEntries(
        Map.entry("113", "晴"),
        ...
);
```

`Map.ofEntries` 创建的是**不可变 Map**——常量一旦定义就不能改，防止代码别处不小心改坏。它是 Java 9+ 的不可变集合之一，配 `static final` 是标准姿势。

## 六、失败兜底 —— 海外服务不稳

```java
} catch (Exception e) {
    return city + "天气暂时查询不到（服务不稳定），请稍后再试。";
}
```

wttr.in 是海外服务，国内访问**偶发慢/不稳定**。这里不抛异常打断对话，而是返回一句兜底文案——模型拿到这句，会组织成"抱歉查不到"的回答。**工具要能容错**：一次工具调用失败不该毁掉整个对话。

## 七、为什么工具不用在 Controller 暴露 HTTP 接口

因为 Function Calling 的调用路径是 **模型 → Spring AI → 工具方法**，全程在 JVM 内部完成，不需要 HTTP。Controller 只对外暴露"人"用的接口，工具是"模型"用的接口——两套通道，互不干扰。
