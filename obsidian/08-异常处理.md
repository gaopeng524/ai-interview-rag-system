# 08 · 异常处理

覆盖：`BusinessException` + `GlobalExceptionHandler`。核心是**一处抛出，全局兜底**——Service 只管 `throw`，HTTP 层的"怎么变成 JSON 响应、打什么日志"全交给全局处理器。

## 为什么需要全局异常处理

不加任何处理时，Service 抛个异常，Spring 会返回一坨英文错误页（带堆栈），前端没法解析、用户看不懂、日志还刷屏。全局处理器的价值：

1. **统一响应格式**：所有错误都是 `{code, message, detail, time}` 的 JSON，前端一种解析方式全搞定。
2. **分级日志**：资源不存在/客户端断连是"正常情况"（INFO），业务异常是"预期内的失败"（WARN），真正的兜底才是"服务器内部错误"（ERROR）。日志量立刻变干净。
3. **状态码正确**：登录失败是 401 不是 500，资源不存在是 404 不是 500。

## BusinessException —— 带状态码的业务异常

```java
public class BusinessException extends RuntimeException {
    private final HttpStatus status;

    public BusinessException(HttpStatus status, String message) {
        super(message);
        this.status = status;
    }

    public HttpStatus getStatus() { return status; }
}
```

设计要点：
- 继承 `RuntimeException`：**不用在方法签名里 `throws`**，可以穿透所有层直接到处理器。
- 自带 `HttpStatus`：抛出时就把"该返回什么状态码"写死了，处理器不用猜。
- 使用方式（来自 `UserService.login`）：
```java
throw new BusinessException(HttpStatus.UNAUTHORIZED, "用户名或密码错误");
```

一句话理解：**它是一个"会说话"的异常，自己告诉 Spring 该回什么状态码、什么文案。**

## GlobalExceptionHandler —— 四个处理器

```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {
```

`@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`：**全局的、自动响应 JSON 的异常处理切面**。它监控所有 Controller，任何异常都会先来这里找匹配的处理器。

### ① NoResourceFoundException → 404

```java
@ExceptionHandler(NoResourceFoundException.class)
public ResponseEntity<Map<String, Object>> handleNotFound(NoResourceFoundException e) {
    log.info("资源不存在：{}", e.getResourcePath());
    return build(HttpStatus.NOT_FOUND, 404, "资源不存在", e.getResourcePath());
}
```

处理"URL 或静态资源不存在"。专门单独建一个处理器而不丢给 500 兜底，是因为：**浏览器会自动请求 `/favicon.ico` 这类资源**，不存在是常态，不该刷 ERROR 日志。给最具体的异常建最具体的处理器，正是 `@ExceptionHandler` "**优先匹配最具体的异常类型**"的原则。

### ② AsyncRequestNotUsableException → 什么都不做

```java
@ExceptionHandler(AsyncRequestNotUsableException.class)
public void handleClientDisconnect(AsyncRequestNotUsableException e) {
    log.info("客户端断开连接（流式请求提前关闭）：{}", e.getMessage());
}
```

这个专门为 **SSE 流式**设计的处理器，非常巧妙。场景：用户聊到一半关掉浏览器/刷新页面 → 服务器还在往外推数据 → 客户端没了 → Spring 抛 `AsyncRequestNotUsableException`。

**为什么返回 void**：这时候响应通道已经断了，如果再去写 JSON，会再抛一次 `HttpMessageNotWritableException`，把"正常断连"搞成 500 刷错误日志。返回 void 就是**承认"响应已经没法用了，随它去"**，只打一条 INFO。

### ③ BusinessException → 按自带状态码返回

```java
@ExceptionHandler(BusinessException.class)
public ResponseEntity<Map<String, Object>> handleBusiness(BusinessException e) {
    log.warn("业务异常：{}", e.getMessage());
    return build(e.getStatus(), e.getStatus().value(), e.getMessage(), null);
}
```

业务异常是**预期内的失败**（登录失败、无权访问），打 WARN 不打 ERROR——它不是程序 bug，是用户输入导致的正常分支。

### ④ Exception → 500 兜底

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Map<String, Object>> handleException(Exception e) {
    log.error("未捕获异常，返回 500 兜底。异常类型：{}，信息：{}",
            e.getClass().getName(), e.getMessage(), e);
    return build(HttpStatus.INTERNAL_SERVER_ERROR, 500, "服务内部错误", e.getClass().getSimpleName());
}
```

最后一个处理器是**兜底**：所有没被上面三个接住的异常都到这儿。打 ERROR 带完整堆栈（`e`），响应只给 `{code:500, message:"服务内部错误"}`——**不给前端看堆栈详情**（那是给开发者的，暴露给用户是安全隐患）。

### 统一 build 方法

```java
private ResponseEntity<Map<String, Object>> build(HttpStatus status, int code,
        String message, String detail) {
    Map<String, Object> body = new LinkedHashMap<>();
    body.put("code", code);
    body.put("message", message);
    body.put("detail", detail);
    body.put("time", LocalDateTime.now().toString());
    return ResponseEntity.status(status).body(body);
}
```

`LinkedHashMap` 保证字段顺序稳定（`code → message → detail → time`）。所有错误响应都是这个形状，前端统一解析。

## 匹配优先级

```
异常进来
  ├─ 是 NoResourceFoundException？   → 404（INFO）
  ├─ 是 AsyncRequestNotUsableException？ → void（INFO）
  ├─ 是 BusinessException？          → 自带状态码（WARN）
  └─ 其他任何异常                     → 500（ERROR）
```

`@ExceptionHandler` 会自动选**最具体**的处理器，所以 `Exception` 兜底永远不会抢走前三者的活。

## 这个设计让调用方变得干净

```java
// Service 里，业务逻辑只管 throw，不用 try-catch 包装成响应
if (!matches) {
    throw new BusinessException(HttpStatus.UNAUTHORIZED, "用户名或密码错误");
}
```

**职责分离**：Service 懂业务，不懂 HTTP；Handler 懂 HTTP，不懂业务。中间靠一个自带状态码的异常衔接。
