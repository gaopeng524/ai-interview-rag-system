# 07 · 数据访问层

覆盖：`entity`（表镜像）、`dto`（报文）、`mapper`（接口 + XML）、表结构。核心是理解 MyBatis 的"接口 ↔ XML ↔ SQL"三角关系。

## Entity —— 表的镜像

```java
@Data   // Lombok：自动生成 getter/setter/toString/equals/hashCode
public class User {
    private Long id;
    private String username;
    private String password;
}
```

三个实体，各对一张表：

| Entity | 表 | 关键字段 |
|---|---|---|
| `User` | `users` | id, username, password(哈希) |
| `ChatSession` | `chat_sessions` | id, user_id, title, created_at, updated_at |
| `ChatMessage` | `chat_messages` | id, session_id, role(user/assistant), content, created_at |

**`@Data` 是 Lombok 的注解**：一个注解省掉几十行样板代码。编译时自动生成 `getId()`、`setUsername()` 这些。Spring Boot 3.2+ / 新版已经内置 Lombok 支持，直接用。

## DTO vs Entity —— 为什么两套

| | Entity | DTO |
|---|---|---|
| 对应 | 数据库表列 | 与前端约定的报文 |
| 内容 | 完整字段（含 password） | 脱敏（`UserResponse` 只有 id+username） |

**规则**：实体不出 Controller。否则 `User` 实体的 `password` 字段会被 JSON 序列化发给前端。DTO 就是"对外只给该给的"。

## Mapper —— 接口只声明，SQL 在 XML

`UserMapper.java`：
```java
@Mapper
public interface UserMapper {
    List<User> findAll();
    User findById(Long id);
    int insert(User user);
    User findByUsername(String username);
}
```

`UserMapper.xml`：
```xml
<mapper namespace="com.example.demo.mapper.UserMapper">

    <select id="findByUsername" resultType="com.example.demo.entity.User">
        SELECT id, username, password
        FROM users
        WHERE username = #{username}
    </select>

    <insert id="insert" useGeneratedKeys="true" keyProperty="id">
        INSERT INTO users (username, password) VALUES (#{username}, #{password})
    </insert>
</mapper>
```

MyBatis 怎么知道接口方法对应哪段 SQL？**靠 `namespace + id` 拼接**：
- XML 的 `namespace` = 接口全限定名
- XML 的 `id` = 接口方法名

`userMapper.findByUsername("alice")` → MyBatis 找到 `UserMapper.findByUsername` → 执行那段 SELECT → 结果按 `resultType` 自动映射成 `User`。

### `#{}` 和 `${}` 的区别（面试高频）

```xml
WHERE username = #{username}   -- ✅ 预编译参数，防 SQL 注入
WHERE username = ${username}   -- ❌ 字符串拼接，能注入
```

`#{}` 会把值用占位符 `?` 传给数据库预编译语句，值是数据不是代码。**永远用 `#{}`**。

### `useGeneratedKeys` —— 自增 id 回填

```xml
<insert id="insert" useGeneratedKeys="true" keyProperty="id">
```
插入后数据库生成的自增 id 会**自动写回对象的 id 字段**。这就是为什么 `ChatSessionService.create` 插入后直接 `return session`，前端能拿到 `session.id`——MyBatis 已经替我们把 id 填进去了。

### 三个 XML 的职责一览

| XML | 有哪些语句 |
|---|---|
| `UserMapper.xml` | findAll, findById, findByUsername, insert |
| `ChatSessionMapper.xml` | insert, findByIdAndUserId, findByUserId, deleteById |
| `ChatMessageMapper.xml` | insert, findBySessionId, deleteBySessionId |

## 归属校验的 SQL 长什么样

```xml
<select id="findByIdAndUserId" resultType="com.example.demo.entity.ChatSession">
    SELECT id, user_id, title, created_at, updated_at
    FROM chat_sessions
    WHERE id = #{id}
    AND user_id = #{userId}   <!-- 存在 和 属于你 一次查完 -->
</select>
```

注意 SELECT 里**显式列出列名**而不是 `SELECT *`：避免查了不用的列、防止 `user_id` 列名和实体字段对不上。`findByUserId` 用 `ORDER BY created_at DESC` 让最新会话在最上面。

## 表结构（PostgreSQL，Docker ai-postgres 容器）

```sql
-- users
id BIGSERIAL PRIMARY KEY,
username VARCHAR UNIQUE,
password VARCHAR          -- BCrypt 哈希，绝不能明文

-- chat_sessions
id BIGSERIAL PRIMARY KEY,
user_id BIGINT REFERENCES users(id),
title VARCHAR,
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMP

-- chat_messages
id BIGSERIAL PRIMARY KEY,
session_id BIGINT REFERENCES chat_sessions(id),  -- 外键：删会话要先删消息
role VARCHAR(20),        -- 'user' | 'assistant'
content TEXT,
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

**外键 `session_id REFERENCES chat_sessions(id)`** 是 `ChatSessionService.delete` 里"先删消息再删会话"的原因——外键约束不允许直接删被引用的父行。
